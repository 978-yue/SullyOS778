# 存钱罐 App「咖啡馆经营」重启 PRD + 美术美化报告

> 产品经理视角的诊断与需求文档。团队约束：**代码团队可用，美术团队几乎不存在**。
> 结论先行：现有"模拟经营游戏"不是没做好，而是**经济循环从未闭合，游戏根本没有启动**。
> 重启方向：**文字驱动的经营游戏** + 全面复用现有素材（Twemoji CDN、娃娃屋渲染器、角色系统、LLM 管线），零新增美术依赖。

---

## 一、现状诊断：为什么"模拟经营"没能启动

以下每一条都有代码证据，不是感觉。

### 1.1 经济循环断裂（致命）

现在的资源流是一条**单行道**：

```
现实省钱 ──> AP（唯一货币）──> 买员工/食谱/房间 ──> appeal（人气值）──> 【终点，无任何下游】
```

- AP 唯一来源：每日结算一次，`AP = 每日预算 − 昨日花费 + 10 登录奖励`（`apps/BankApp.tsx:239-282`）。默认预算 ¥100，即**每天理论上限约 110 AP**。
- AP 去向全是一次性水槽：食谱 50–500 AP（`components/bank/BankGameConstants.tsx:23-31`）、雇员 150–200 AP、房间解锁 120–300 AP（`components/bank/BankDollhouse.tsx:16-21`）、房型 80–300 AP。
- 所有购买的唯一产出是 `appeal`（`apps/BankApp.tsx:96-103`），而 **appeal 在全部代码中没有任何消费方**：不产生收入、不影响客流、不触发事件。玩家做的每一个"经营决策"都没有反馈。

**这不是经营游戏，是一张消费清单。** 经营游戏的定义是"投入 → 产出 → 再投入"的循环，这里第二步就断了。

### 1.2 死机制清单（代码里的僵尸系统）

| 机制 | 现状 | 证据 |
|------|------|------|
| 储蓄目标进度 | `currentAmount` 创建时为 0，**全仓库无任何写入路径**，进度条永远 0% | `apps/BankApp.tsx:725`；grep `currentAmount` 仅有读取 |
| 员工疲劳 | `fatigue` **只减不增**（每日 −30、休息 −50），永远是 0。"休息"按钮（20 AP）和状态灯都在演戏 | `apps/BankApp.tsx:265,385`；无任何 `fatigue` 增加代码 |
| 店铺等级 | `shopLevel` 初始为 1，之后无任何代码修改它 | `apps/BankApp.tsx:26` |
| 人气 appeal | 有计算、有显示，无消费方 | 见 1.1 |
| 访客 activeVisitor | 刷新留言板时随机放一个角色贴图进房间，无任何交互 | `apps/BankApp.tsx:600-615` |
| 宠物系统 | 招聘界面承诺"主人来访触发特殊互动"，该逻辑（`foundPet`）只存在于 `BankShopScene.tsx`——**一个被 import 但从未渲染的死组件**（游戏页实际渲染 `BankDollhouse`）。宠物领养后无任何行为 | `BankGameMenu.tsx:357`、`BankShopScene.tsx:30-39`（无渲染调用点） |

### 1.3 节奏死亡

- 每天封顶约 110 AP，雇一个员工要攒 2 天，解锁 VIP 包间要攒 3 天。
- 一次性内容总池约 2000 AP，买完即"通关"，之后每天登录只剩一件可重复的事：花 40 AP 刷一次留言板。
- 新玩家前 10 分钟：看教程 → 发现什么都买不起 → 关掉。**首日无完整体验循环，留存无从谈起。**

### 1.4 定位自相矛盾

记账（使用产品的核心动作）在游戏机制里是**负反馈**：记一笔 = 今日花费上升 = 明天 AP 减少，超支还会弹警告（`apps/BankApp.tsx:336-338`）。机制在惩罚"诚实记账的人"，而漏记账反而只损失结余——**应该奖励"记账行为"，而不只是奖励"省钱结果"**。

### 1.5 现有的唯一亮点

留言板"打听消息"（`apps/BankApp.tsx:497-627`）：花 40 AP 让 LLM 以角色人设 + 聊天上下文生成八卦小剧场，并回写系统消息到聊天记录。**这是全 App 唯一"活"的内容，也是文字化重启的样板**——它证明了这条管线（ContextBuilder + 角色 + JSON 输出 + 回写聊天）可以低成本量产内容。缺点：无 API Key 时完全不可用，没有本地兜底。

## 二、重启设计原则

1. **文字是主要内容载体。** 美术≈0，但项目有成熟的角色系统、记忆宫殿、ContextBuilder、LLM 管线——文字内容的生产成本趋近于零，且风味远超贴图。
2. **只复用，不新增美术。** Twemoji CDN 图标、娃娃屋渲染器（1700 行，支持墙纸/地板/贴纸/全屋贴图/自定义家具 URL）、CSS 渐变预设、角色头像/Q 版形象，全部现成。
3. **记账是发动机。** 每一次记账都必须在 3 秒内产生游戏反馈，而不是等到明天结算。
4. **LLM 必须有本地文案表兜底。** 无 API Key 也要能完整玩（留言板的教训）。

## 三、需求（按优先级）

### P0 —— 让循环闭合（纯逻辑，零美术）

#### REQ-1 营业结算：给 appeal 一个下游

- 引入第二货币**金币 🪙**（Twemoji `1fa99`，零美术成本）。
- 每日首次打开 App 时结算"昨日营业"：
  `营业额 = appeal × 营业效率`，`营业效率 = 1 − 平均疲劳/200`，`金币 = ⌊营业额 / 10⌋`。
- **双货币分工**：AP（来自现实省钱）只用于**扩张**（雇人/解锁/房型）；金币（来自游戏经营）只用于**表达**（装饰、贴纸、墙纸变体、改名、请角色喝咖啡）。现实行为决定成长速度，游戏产出决定好看程度——两条循环互不通兑，防止刷金币绕过省钱。

#### REQ-2 记账即事件：把"花钱"变成故事素材

- 每记一笔账，立即弹出一条文字事件卡，把消费编织进店铺叙事：
  > 你买了奶茶（¥15）。柴犬服务生闻到了甜味，缠着你要了一口——今日店里甜品话题度 +10%。
- 实现：本地文案表（按 BankAnalytics 已有的 8 个分类 × 各 10+ 条模板，`components/bank/BankAnalytics.tsx:16-25` 的分类和关键词猜测函数直接复用）；配置了 API Key 时可用 LLM 生成变体。
- 超支不再只弹冷冰冰的警告，而是触发"店铺危机"文字事件（明日营业效率小幅下降 + 一条自嘲文案），**有代价但有戏**。

#### REQ-3 复活三个僵尸机制

1. **储蓄目标**：每日结算时，把预算结余自动注入进度最靠前的目标 `currentAmount`（省下的钱视为存进心愿）。达成目标 → 全屏庆祝（纯 CSS confetti）+ 一件限定装饰贴纸 + 一条 LLM/文案表生成的"店铺为你庆祝"小剧场。
2. **疲劳**：员工疲劳随昨日营业额上升（`+⌊营业额/20⌋`，封顶 maxFatigue），疲劳 >80 的员工不计入营业效率 → "休息"按钮（20 AP）第一次有了存在的意义。
3. **店铺等级**：`shopLevel` 由累计营业额驱动（阈值表），升级只解锁**文字称号**（"无名小店"→"街角常客"→"巷子里的传说"）+ 金币商店新档位，不需要任何新美术。

#### REQ-4 每日经营小报（复用留言板 LLM 管线）

- 每日结算时生成一份《昨日店报》：一段 100–200 字的小剧场，嵌入真实数据（昨日记账笔数、结余、营业额、来访角色）。
- 管线 100% 复用 `handleRefreshGuestbook` 的结构（ContextBuilder + JSON 输出 + 回写系统消息）；无 API Key 时用模板拼装（"昨天你省下了 ¥23，柴犬用这笔'工资'进了一批新豆子…"）。

### P1 —— 文字玩法拓展

#### REQ-5 客人委托（事件卡系统）

- 每天刷新 1–3 个文字委托：「一位客人想要一杯完全不加糖的手冲，但棕熊大厨今天心情不好」→ 二选一抉择（安抚大厨 −10 AP / 自己上 −5 AP 但疲劳 +10）→ 产出金币和一句结果文案。
- 文案表驱动（先写 30 张卡），LLM 可选生成变体。这是留存的日常抓手，成本只有文案。

#### REQ-6 角色来访常驻化

- 现有 activeVisitor 从"贴图"升级为"住一天的客人"：来访期间头顶随机气泡台词（LLM 一次生成 3 条缓存，或文案表）；可花 20 金币"请 TA 喝咖啡"→ 触发一段对话并回写聊天系统（复用现有 `systemMessageId` 管线，`apps/BankApp.tsx:572-586`）。
- 立绘 = 现有角色头像/Q 版形象（chibiStudio 字段已有，见 `docs/chibi-studio.md`），零新美术。

#### REQ-7 记账连击（streak）

- 连续 N 天有记账记录 → 金币结算乘数（3 天 ×1.2，7 天 ×1.5，30 天 ×2）。
- **宽容设计**：漏一天只降一档，不清零——目标是养习惯，不是制造焦虑。

#### REQ-8 宠物动态系统「Pet Drama Engine」⭐ 本次重启的差异化玩法

现有基建：宠物领养（150 AP）、`isPet`/`ownerCharId` 字段（`types.ts:1876-1877`）、宠物与角色的归属关系都已存在，只缺"行为"。宠物是**零美术成本的戏剧发生器**：它们不用立绘（现有头像/Twemoji 就够），不用动画（文字 + 表情气泡就够），但能持续产出玩家最爱看的东西——**关系和事故**。

**8a. 宠物关系图谱（数据层）**

- 任意两只宠物之间维护一个关系值 `-100 ~ +100`，存入 `petRelations: Record<pairKey, number>`（并入 dataVersion v3 迁移）。
- 关系值划分五档，只用文字称号，零美术：
  死对头（≤−60）→ 塑料友情（−59~−10）→ 点头之交（−9~+29）→ 形影不离（+30~+69）→ **暧昧期（≥+70）**。
- 关系值只能被"事件"推动，玩家不能直接改——关系是养出来的，不是买出来的。

**8b. 宠物动静（事件层）**

每日结算时掷 1~3 个宠物事件（在店宠物 ≥2 时才触发；只有 1 只时走"独角戏"事件池：拆家、偷吃、对着窗外的鸟发呆）。事件类型与关系值联动：

| 事件类型 | 示例文案 | 关系变化 | 经营影响 |
|----------|---------|---------|---------|
| 打架 💢 | 「柴犬和企鹅为了最后一块曲奇大打出手，吧台遭殃」 | −15 | 当日营业效率 −5%，但店报话题度 +（有戏看客人反而多）|
| 抢食 😤 | 「XT 把兔兔前台的小鱼干叼走了，现场留下一撮毛」 | −8 | 无 |
| 结伴打盹 💤 | 「两只在窗边的阳光里叠成一团睡着了，客人不忍点单」 | +10 | 疲劳 −10 |
| 互相理毛/分享零食 🍪 | 「棕熊大厨偷偷给柴犬留了一块边角蛋糕」 | +12 | 无 |
| **暧昧 💕** | 「打烊后，有人看见两只尾巴缠在一起看月亮…店报记者已就位」 | +18 | 店铺 appeal 临时 +20（八卦引流）|
| 拉帮结派 🐾 | 三只以上时触发：小团体 vs 边缘宠物，产出连续剧式文案 | 多向变动 | 无 |

- 实现：本地事件文案表（每类 ≥8 条模板，代入宠物名字/主人名字），LLM 可选生成变体和"续集"（读取最近 5 条宠物事件做连续性，同 guestbook 的 Continuity 设计）。
- **事件有记忆**：关系档位变化本身是大事件（"官宣"暧昧期、"决裂"成死对头），触发一期店报头条。

**8c. 主人反应（角色层）——本需求的灵魂**

宠物事件涉及 `ownerCharId` 时，以该角色人设生成主人反应，通过现有 `systemMessage` 管线（`apps/BankApp.tsx:572-586`）写回「查手机」聊天：

- 自家宠物被欺负 → 主人在聊天里心疼/兴师问罪；
- **两只宠物进入暧昧期 → 两位主人同时收到消息，各自以人设反应**——尴尬、起哄、吃醋、连夜认亲家——跨角色戏剧凭空产生，这是其他玩法给不了的；
- 主人来访时（REQ-6）发现自己宠物在打工 → 兑现 `BankShopScene` 里那句从未上线的承诺（把死代码里的 `foundPet` 逻辑移植到 `BankDollhouse`，顺手删除死组件）。

**8d. 玩家介入（金币消费点）**

| 操作 | 花费 | 效果 |
|------|------|------|
| 投喂 | 10 金币 | 指定宠物疲劳 −20，随机小文案 |
| 劝架 | 15 金币 | 本次打架关系损失减半，产出调解文案 |
| 撮合 | 20 金币 | 指定两只下次事件必为正向（成功率 70%，失败反弹 −5 并产出"多管闲事"文案）|
| 塞小鱼干打听 | 5 金币 | 查看某只宠物"心里话"（LLM/文案表，视角独白）|

**8e. 宠物职能（功能层，轻量 buff）**

给宠物一个可选被动，让"领养"有经营意义但不破坏平衡：招财（金币结算 +5%）、看店（全员疲劳增速 −10%）、捣蛋鬼（营业效率 −3% 但宠物事件 +1 个/天——**用产出的戏补偿数值损失**，给乐子人玩家的选项）。

**8f. 护栏（评审红线）**

1. **暧昧 = 萌向拟人**，文案表全部走"尾巴缠一起/分零食/看月亮"路线，PG 分级；LLM prompt 中明确约束基调。
2. **写回聊天要节流**：每角色每天最多 1 条宠物相关系统消息，可在设置中按角色关闭——不能让店里的狗把用户和角色的聊天记录淹了。
3. 主人反应必须过 ContextBuilder 走完整人设，不允许通用模板冒充角色口吻。
4. 无 API Key 时事件、独白、主人反应全部有文案表兜底（主人反应兜底 = 通用模板 + 角色名，标注"简讯"样式以示区别）。

### P2 —— 长线

## 四、美术美化报告（零/低成本方案）

### 4.1 现有资产盘点（全部可直接复用）

| 资产 | 位置 | 复用方式 |
|------|------|---------|
| Twemoji CDN 全套图标 | `BankGameConstants.tsx`（食谱/员工/贴纸/家具已在用） | 唯一图标源，金币=`1fa99`，新事件卡图标从 72×72 库里选，**禁止引入第二图标体系** |
| 娃娃屋渲染器 | `BankDollhouse.tsx`（墙纸/地板/贴纸拖拽/全屋贴图/自定义家具 URL 全支持） | 新玩法一律不碰渲染层，全部落在文字层和数据层 |
| CSS 渐变预设 | 墙纸 8 套 + 地板 6 套（`BankGameConstants.tsx:111-129`） | 金币商店直接卖"配色变体"——改渐变色值即新商品，**代码生成，零美术** |
| 角色头像 / Q 版形象 | 角色系统 + chibiStudio | 角色来访立绘、事件卡头像 |
| 现有咖啡色系 UI | `#FDF6E3 / #8D6E63 / #FF7043 / #E8DCC8` | 见 4.3 色彩规范 |

### 4.2 新增视觉全部用「排版」解决

美术团队不存在，所以美化的武器是**字体、留白、边框、纸感**——全是 CSS：

1. **文字事件卡 = 收银小票**：等宽字体（`font-mono`，项目已在用）、上下虚线裁切边（`border-dashed`）、微倾斜 1° 、顶部一行 `☕ COFFEE TYCOON — RECEIPT`。信息即装饰。
2. **每日店报 = 报纸头版**：衬线标题 + 细分栏线 + "第 N 期"期号（期号 = 开业天数，白送仪式感）。与留言板"店铺情报志"共用视觉语言。
3. **结算面板**：纯 CSS 数字滚动（`@keyframes` 位移）+ 达成目标时 confetti（Phosphor `Confetti` 图标 + 现有 `animate-fade-in` 体系扩一个 `animate-pop`）。
4. **空状态文案化**：项目已有好苗子（"风中什么声音都没有…"，`apps/BankApp.tsx:930`）。把所有空状态都写成有味道的句子，这是**成本最低、感知最强**的美化——每个空状态配一句店铺口吻的话 + 一个大号半透明 Twemoji。
5. **称号系统零图标**：店铺等级称号用文字 + 渐变描边字（`background-clip: text`）呈现，不做徽章图。
6. **宠物动静的视觉呈现（REQ-8）零新美术**：娃娃屋里两只宠物发生事件时，复用现有 actor 定位系统（`x/y` 百分比 + 拖拽已支持）让它们**慢慢飘向对方**，头顶弹 Twemoji 情绪气泡（💢 打架 / 💤 打盹 / 💕 暧昧 / 🍪 分零食）+ 一次 CSS 摇晃或弹跳动画。关系档位在员工卡上用文字小徽章显示（"与柴犬：暧昧期 💕"）。全部是已有素材 + CSS。

### 4.3 视觉规范（防止越改越花）

- **锁死色板**：只允许现有咖啡色系 6 色 + 功能色（绿/红/蓝各一），任何新界面不得新增颜色。
- **锁死圆角与投影**：沿用现有 `rounded-xl/2xl` + 柔和投影，不引入新风格。
- **图片三来源原则**：Twemoji CDN / 角色头像 / 用户自传 URL——除此之外不出现任何图片资源，保证包体和加载稳定。
- 现有界面本身质感不差（渐变头部、毛玻璃、卡片体系是完整的），**问题从来不是"丑"，是"没东西可玩"**。美化预算的 80% 应花在文案表上。

## 六、风险

1. **LLM 依赖**：所有 LLM 功能必须先落本地文案表，LLM 是增味剂不是主食。
2. **数值失衡**：金币通胀会杀死装饰的稀缺感——商店价格表放常量文件，便于热调。
3. **迁移**：老存档 `dataVersion<3` 的补偿逻辑要在 `loadData` 现有迁移链（`apps/BankApp.tsx:189-234`）末尾追加，模式已成熟。
4. **别再惩罚记账**：任何新机制评审时先问一句——"这会让用户少记一笔账吗？"会，就砍。
5. **宠物戏别刷屏**：REQ-8 写回聊天的系统消息是把双刃剑——节流上限（每角色每天 1 条）与按角色关闭开关必须和功能同版本上线，不能后补。
6. **暧昧基调失控**：LLM 生成的宠物暧昧/主人反应必须带基调约束提示词，文案表兜底作为基调锚点；上线前用现有 dev 调试面板（`docs/dev-debug.md`）抽查一批生成样本。
